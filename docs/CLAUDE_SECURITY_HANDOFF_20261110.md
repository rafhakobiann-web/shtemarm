## Confirmed findings and changes
1. **CRITICAL — public full banks + answer keys**. `src/lib/books.ts` uses `fetchBookResponse('/data/*.json')` and the files (including Biology III/IV supplements) are in `public/data`. Direct URL access bypasses the guest UI limit; answer keys are embedded in JSON. `src/lib/mcp/tools/get-questions.ts` also fetches public banks and returns keys under OAuth. Do not claim questions are protected until direct unauthenticated URL access is eliminated. Existing publicly cached copies may need invalidation.
2. **DB permissions**. SQL migration `supabase/migrations/20261110140000_restrict_client_grants.sql` was created here. The equivalent SQL was submitted successfully to the **production Lovable Supabase database**: revoke direct anon/auth privileges on `explanation_cache`, revoke all anon privileges on `user_progress`, allow authenticated SELECT/INSERT/UPDATE only, and revoke browser access to `feedback`. All three tables had RLS enabled; existing `user_progress` policies restrict rows by `auth.uid() = user_id`. **Important**: immediate post-write SQL verification was blocked by the Lovable free-plan MCP query limit; independently re-run the verification before declaring success. No rows were deleted.
3. **Admin privilege hardening staged in this branch**. `src/lib/admin-session.server.ts` now requires a non-empty `ADMIN_ALLOWED_USER_IDS` allowlist after server-side `supabaseAdmin.auth.getUser(token)`. `src/lib/feedback.functions.ts` admin actions call the same verifier. `src/test/admin-session.test.ts` covers unset allowlist. **Before merging**, put the exact owner's Supabase Auth user UUID in Lovable server-only `ADMIN_ALLOWED_USER_IDS`; otherwise all admin operations intentionally fail closed. Keep `ADMIN_PASSWORD` secret and configure MFA on the owner's auth account. Never commit IDs, tokens, or secrets.
4. **Protected data already using RLS**. `user_progress` has owner-only SELECT/INSERT/UPDATE policies. `feedback` and quota counters have no public table privileges; the quota RPCs are SECURITY DEFINER but EXECUTE is only granted to service_role. Protect their privileges during future migrations.
5. **HTTP baseline already exists**. `src/lib/security-headers.ts` sets nosniff, limited CSP, HSTS and no-store on account/API responses; `src/server.ts` uses it. CSP currently lacks a strong `script-src` nonce/hash design because TanStack Start streams inline scripts. Do not blindly insert `script-src 'none'` or break Lovable editor framing/OAuth. `src/start.ts` installs CSRF request middleware for server functions.
6. **AI server calls**. `src/lib/ai-quota.server.ts` validates Supabase Auth bearer tokens before reserving remote AI spending. `explain.functions.ts` and `chat.functions.ts` rely on that guard; inspect all future call paths. Cached/offline explanations may be accessible to guests by design; never disclose per-user or secret content from cache.
7. **GitHub CI blocker**. On PR #265, 15 GitHub Actions runs failed, each verify job ended before producing steps/logs. This does **not** prove code failures or success. Investigate GitHub Actions account/runner limits and re-run actual typecheck/build/Vitest. No production success claims based only on successful GitHub merge or Lovable sync.
8. **Client isolation issue to audit**: `src/lib/progress.ts` uses one device-wide `localStorage` key `shtemaran-progress-v1` and merges it into whichever account logs in. Test shared-device account switching and logout; plan migration to per-user keys without losing old data or leaking one student's progress to another.
9. **Repo hygiene**: existing `.github/workflows/repository-security.yml` scans for tracked/historical secrets. Re-run; rotate any exposed secret. Prefer GitHub secret scanning/dependency alerts, pinned actions, Dependabot and a lockfile audit.

## Required P0 work — make access genuinely server-enforced
A. Store the **full original question-bank JSON and answer keys outside any web-served `public` path**, preferably in private object storage or a server-only store. Avoid simply renaming, hiding links, adding a robots.txt, or relying on route guards/CORS. Revise every client-side loader, including `src/lib/books.ts`, exam modes, search, English preview and Biology supplements; inspect `src/lib/mcp` as well. Do not break Lovable production routing.
B. Provide an authenticated, server-verified `GET/POST` API to fetch full book sections. Validate Supabase bearer tokens **server-side** via `getUser()` (or suitable verified JWT claims), authorize the requested book/section and return `Cache-Control: private, no-store`. Treat missing/expired/unknown tokens as unauthenticated, fail closed. Never use a service role key in frontend bundles.
C. Serve only two **approved** complete preview tasks (or two reading passages) for each guest section, through a separately allowed endpoint. Do not return the entire book to the browser and slice it on the client. For answer checking, grade guest answers on the server (never send complete correct answer keys with the preview). Ensure multipart biology scoring stays correct. A disposable cookie is insufficient as the *sole* defense against bulk extraction; combine strict scope, validation and rate limits.
D. Ensure privileged paths (test/exams, tutoring, question sources, admin, user data, library APIs, MCP tools) cannot leak full banks without verified authorization. Add tests that directly request the raw `/data/book1.json`, `/data/bio-book3.json`, `/data/biology-pending-book4.json` and analogous files and expect **404/403**, including attempts to use cached public URLs. Remove old served artifacts from the final deployment output.
E. Keep all existing question IDs, per-section ordering and `user_progress` mappings; migrate additively. Existing progress must remain accessible for the original account. Do a backfill/dual-read strategy rather than overwriting historical local progress.
F. Explicitly decide the offline tradeoff: an entire offline-readable answer bank cannot simultaneously be secret from that client. Protected full banks may need network access; keep an explicitly small public/offline demo instead.

## P1 / operational work
- Turnstile/CAPTCHA and shared IP/identity quotas for guest feedback/login endpoints (clientId alone is not strong abuse prevention).
- Security logging without PII/secrets; monitor unusual download rates, failed logins, quota requests and service health.
- Implement nonce/hash-based CSP compatible with the actual TanStack/React and Lovable editor preview; audit `dangerouslySetInnerHTML` outputs (KaTeX sanitization).
- Security-conscious auth token/session handling, device logout and localStorage user isolation.
- Cloudflare WAF / rate-limiting on custom domain, while recognizing `shtemarm.lovable.app` traffic can bypass custom-domain Cloudflare settings unless the origin has equivalent protections. Avoid untested rules that block legitimate students.
- Dependency/OSV audits, Renovate/Dependabot, strict CI gates, branch protection if repo plan supports it.
- Check data licensing and maintain traceability of Biology and other official source content.
